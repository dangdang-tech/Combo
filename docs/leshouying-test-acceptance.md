# 乐收赢充值验收记录与退役边界

日期：2026-09-11

## 当前结论

Authoring API 继续提供钱包读取、充值产品、手动金额创建订单、按订单查询、按 `rechargeIntentId` 恢复、支付通知和应用内主动查单。乐收赢二维码支付使用 C扫B `/v3/prepay`，查单使用 `/v3/queryorder`；浏览器返回结果不会直接改变余额，只有验签通知或原订单查单确认成功后才会在数据库事务中完成订单、钱包和不可变 credit 流水。

旧 Web Runtime 与 Agent 固定按次计费执行链已经退出主栈。历史数据库迁移和资金记录保持不变，但仓库不再提供 Session、Turn、402 恢复、免费次数或 Runtime 扣费入口。过去的真实支付与固定按次验证只能作为历史证据，不能描述为当前端到端 Agent 使用链路。

## 当前充值边界

- 已登录用户以幂等 `rechargeIntentId` 创建充值订单，金额以规范的分字符串进入严格合同。
- 测试和正式网关由固定枚举选择；正式网关还需要生产环境和显式开关共同成立。
- 有副作用的下单请求有总超时且不自动重试。结果不确定时只查询原 `pay_trace_no`，不创建新支付流水。
- 网关响应与通知都要验签，并核对环境、机构、商户、金额和平台订单号。
- 通知与主动查单复用同一个事务入账函数；重复通知不能生成第二条 credit 流水。
- 前端只展示 API 允许的支付动作，并只轮询 Combo 内部订单状态。
- 迟到成功仍可入账；删除旧执行栈不授权删除订单、钱包、流水或历史数据库数据。
- Resend 与支付供应商不参加 `/ready`，避免外部供应商故障阻断已有会话和只读业务；创建验证码或支付订单仍按各自边界失败关闭。

## 配置与安全

- 乐收赢配置只注入 Authoring API；主栈没有后台 Worker 或 Runtime 进程。
- 支付配置缺省时网关关闭。启用后缺少机构、商户、密钥或合法 HTTPS 回调地址会拒绝启动。
- 支付 Secret 只通过 Secret 引用或进程环境注入，不进入仓库、ConfigMap、日志或测试输出。
- 错误响应只返回安全人话、动作、可否重试和低敏 traceId，不返回机构密钥、签名原文、供应商正文或内部错误码。

## 源码验收

使用 Node.js 24 运行 Shared、Authoring 和 Web 的构建、类型检查与测试，并运行数据库迁移、支付签名、回调幂等、主动查单和发布脚本合同测试。没有可达测试 PostgreSQL 时，明确依赖外部数据库的套件会按测试配置跳过；不得把跳过描述为通过。

真实渠道或环境验收必须另获部署与支付授权，并绑定精确提交、环境、内部订单号、金额、支付/入账状态、流水数量、事件时间和低敏 traceId。不得保存或输出机构密钥、完整回调、完整签名串、完整收银台 URL、付款码或 openid。
